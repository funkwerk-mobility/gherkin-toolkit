# Cucumber tests for Cuke

Research snapshot: 2026-11-28. This is a recommendation, not a benchmark or an implementation plan that has already been adopted.

## Recommendation

Keep Vitest and try Cucumber.js for a small set of user-facing CLI acceptance scenarios. Do not replace the full suite. Compare a representative pilot with the equivalent existing tests before deciding whether to migrate more. Cucumber is useful when a feature file itself communicates a behavior that a user or collaborator can review; a test runner alone does not make a scenario readable.

The immediate readability issue can also be fixed without changing runners: use JavaScript template literals for multiline examples or checked-in `.feature` fixtures read as exact bytes. This preserves existing tests and lets the editor display Gherkin naturally. For malformed input, significant trailing newlines, indentation, tabs, or exact formatting output, keep byte-exact fixtures or explicit escapes where needed.

## Current suite

The existing [test script](../package.json) builds TypeScript and runs Vitest. Most tests exercise the compiled CLI as a subprocess with a temporary workspace via [the fixture helper](../test/fixtures.mjs), rather than testing internal functions. Examples include [spelling tags](../test/dotted-tags.test.mjs), [formatting and idempotence](../test/format.test.mjs), and an [interactive terminal driver](../test/configure.test.mjs). Many feature inputs and expected output are embedded as strings with `\n`, obscuring their Gherkin shape. The Vitest configuration already allows 15 seconds per test because CLI startup and dictionary loading can be slow on CI ([configuration](../vitest.config.mjs)); this is not a measurement of framework overhead.

The project already has the official Gherkin parser, but Cucumber.js is a separate [development dependency](https://cucumber.io/docs/installation/javascript/). Cucumber step definitions match feature steps and execute JavaScript ([step definitions](https://cucumber.io/docs/cucumber/step-definitions/?lang=javascript)); they could invoke exactly the same CLI seam. Its [World](https://github.com/cucumber/cucumber-js/blob/main/docs/support_files/world.md) gives each scenario isolated state and [hooks](https://github.com/cucumber/cucumber-js/blob/main/docs/support_files/hooks.md) can create and remove a temporary directory. The current helper imports Vitest's `onTestFinished`, so it cannot simply be reused unchanged: extract framework-independent workspace/CLI operations or provide equivalent Cucumber hooks. Preserve separate HOME and XDG configuration, exit status, stdout/stderr, file contents, cleanup and offline behavior.

## What Cucumber adds—and where it does not

- Executable `.feature` files could explain Cuke's observable behavior in the same language users work with. Suitable pilots include spelling-language overrides, an unknown-word diagnostic with its location, or formatting a feature and running the formatter again to show idempotence. Keep expected results explicit and assert exit status and diagnostics, not just that commands run.
- Run Cuke on the outer, executable `.feature` files in CI to dogfood formatting, spelling and eventually linting. Select a stable configuration and project vocabulary. This is a *separate* check from running those scenarios in Cucumber; executing them does not automatically run Cuke.
- The feature-under-test often has to appear inside a Gherkin docstring or in a separate fixture. An outer feature that contains a feature in a docstring is not the same as Cuke parsing that inner feature: the inner document must be written to a temporary `.feature` and passed to the CLI. Run Cuke against input fixtures separately where appropriate. Intentionally invalid or intentionally misformatted inputs cannot all pass Cuke's normal checks; place them separately and test expected failures, rather than making dogfooding hide or sanitize them.
- Cucumber [docstrings](https://cucumber.io/docs/gherkin/reference/#doc-strings) are dedented relative to the opening delimiter; step definitions receive the parsed content, not necessarily a byte-for-byte copy of the source block. Decide explicitly whether to add a terminal newline, and use separate raw fixture files for exact whitespace, invalid syntax, embedded delimiters, CRLF, and diagnostic-position tests. Backtick docstring delimiters can contain triple-double-quote Gherkin snippets, though editor support varies. Do not assume a docstring can represent all malformed source bytes unchanged.
- Keep detailed boundary and regression tests, formatter byte comparisons, JSON schemas, configuration merging, and interactive wizard/terminal mechanics in Vitest unless a Gherkin scenario actually improves them. Vitest supports reusable [test fixtures](https://vitest.dev/guide/learn/setup-teardown#fixtures-with-test-extend); the current CLI fixture approach already tests behavior. Translating every assertion to general-purpose steps risks verbose, indirect specifications and a large test-specific language.
- A Cucumber scenario with generic “write file/run command/assert text” steps remains an executable integration test, but may not explain intent any better than concise Vitest code. Prefer domain-oriented steps and a small stable vocabulary; keep raw file setup available when the precise input is the point.

## A measured pilot

1. Make a small readability-only improvement to one or two representative Vitest tests using multiline literals or real fixtures. Capture the exact prior content and assertions; preserve final newlines and whitespace. This gives a fair baseline rather than comparing Cucumber against avoidably unreadable strings.
2. Add a few Cucumber.js scenarios covering one spelling override, one diagnostic with a location, and one format/fix/idempotence behavior. Run through the compiled CLI in isolated temporary workspaces. Keep the Vitest originals until equivalent coverage is demonstrated; include an intentionally invalid or whitespace-sensitive case to expose fixture limitations.
3. Add a CI command that checks the outer Cucumber features with Cuke, and explicitly account for input fixtures that are meant to fail. The tests of Cuke must not rely solely on Cuke's own success as their oracle: independently assert output and expected file bytes.
4. Compare readability for maintainers and authors, amount of support code, quality of failures and diffs, CI setup, and median and spread of repeated local/CI runs. Compare a clean build and equivalent selected scenarios; include subprocess startup and dictionary loading. Both runners can run in parallel ([Cucumber](https://github.com/cucumber/cucumber-js/blob/main/docs/parallel.md), [Vitest](https://vitest.dev/guide/parallelism)); neither parallelism nor a particular speed advantage should be assumed without measurement.
5. Adopt a mixed suite if the pilot earns its maintenance cost. Keep one command that runs both suites for CI and contributors, and document how to run each subset.

## Compatibility

Check the exact release selected at implementation time. The inspected Cucumber.js [development-branch package manifest](https://github.com/cucumber/cucumber-js/blob/main/package.json) advertises Node `22 || 24 || >=26`; Cuke currently advertises Node `>=22.18.0` ([manifest](../package.json)). These ranges are not identical: a future test dependency may narrow supported contributor/CI Node versions even if it does not affect users of the published runtime package. Verify the released package's engines, release-specific documentation, licenses, and lockfile before adding it.
